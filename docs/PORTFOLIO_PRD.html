01Product Overview

1.1 Problem statement

A final-year Computer Science student with five substantial, self-built applications and no professional employment history needs a way to be evaluated on engineering ability rather than on résumé length. A conventional CV compresses five complete systems into five bullet points and discards everything that makes them evidence: the architecture, the trade-offs, and the problems that were genuinely hard to solve.

The portfolio exists to close that gap. It is the artefact a recruiter or engineering manager reads instead of, or alongside, the CV.

1.4 Explicit non-goals

  • Not a blog. Rejected — the owner is not committed to writing regularly, and a stale blog is worse than none.
  • Not an AI showcase. No AI/ML skills section, no chatbot assistant. The owner is at the learning stage and declined to claim otherwise.
  • Not a design showpiece. Motion supports hierarchy and never precedes content. No particle fields, cursor trails, or entry animations.
  • Not a CV replacement. A résumé PDF is offered as a download; the site does not attempt to replicate it.

The pattern

Every project is a role-based, multi-actor system with authentication, a relational database, and a decoupled React/DRF architecture. That repetition — not any single project — is the portfolio's central claim.

1. MicroMart

E-commerce

Multi-role e-commerce platform with integrated payments.

React SPA → Django + DRF (JWT verified) → MySQL  ·  branch: SSLCommerz
Problem
A working e-commerce system is several overlapping applications. Customer, seller and administrator each need a different view of the same data with different permissions over it.
Approach
Fully decoupled: React SPA holding no server state, Django + DRF API owning all of it, MySQL underneath. JWT identifies which of three user types is making each request. Payments via SSLCommerz.
Hardest problem
The complete order and payment workflow. Taking a payment is simple in isolation; keeping order, inventory and payment state consistent is not. Users abandon payments mid-flow, gateway callbacks arrive late or twice, and inventory must not be decremented for an unpaid order. Defining the states and their legal transitions was the bulk of the work.
Lesson
The interesting part of a feature is usually its failure cases. Once order states were explicit, most conditional logic scattered through the views disappeared.
Features (15)
Registration & authentication · product search · voice search · shopping cart · payment processing · product reviews · order tracking · store management · product & inventory management · sales analytics · pricing management · user management · complaint management · fraud monitoring · seller verification
Repository
github.com/jhraihan/MicroMart

2. EduFlow

EdTech

Role-based learning management system.

React + Vite (role-aware UI) → DRF (permission layer) → Database
Problem
A learning platform is defined by who may do what. Teacher, student and administrator act on the same records with very different rights.
Approach
Role-based access control across three roles, enforced at the API and reflected in the interface. JWT authentication with lookup by phone number. Client state deliberately handled by native React hooks with no external state library.
Hardest problem
Keeping one set of permission rules authoritative. Every endpoint must answer two questions, not one: may this user perform this action, and on which records. Answering only the first leaves a teacher able to reach another teacher's course by changing an id in the URL. The resolution: the interface never decides access — the API scopes every queryset by role, and the frontend hides controls purely as a convenience.
Lesson
Roles designed in from the start stay in one place; roles added afterwards become scattered conditionals. Building the frontend with only useState, useEffect and Context established firsthand where that stops being sufficient — for this size of application, it never did.
Features (8)
Role-based access control · phone-based JWT authentication · course & lesson management · assignments & submissions · enrolment management · results · server-driven notifications · confirmation dialogs
Repository
github.com/jhraihan/Learning-Management-System-django-react

3. IntelliChat

AI Application

Streaming AI chat application with persistent conversations.

React (SSE listener) → Django (stream relay) → PostgreSQL  ·  branch: Gemini API
Problem
A chat interface that waits for a complete model response before showing anything feels broken even when working. The response must arrive progressively and survive a page reload — both requirements change how the backend is built.
Approach
Django streams the model response over Server-Sent Events rather than returning a completed reply. Conversations and messages persist in PostgreSQL. Responses render as Markdown with syntax highlighting and a copy-code control.
Architecture detail
React posts to /api/chat/. Django calls Gemini and streams back a sequence: a meta event, repeated delta events carrying generated text, then a terminating done or error event.
Hardest problem
Streaming abandons the familiar request/response shape — the connection stays open while text arrives in fragments. A stream can also end in more than one way: complete, fail midway, or the client disconnects during generation. The explicit event protocol exists so the frontend always knows which occurred, rather than inferring it from a stream that simply stopped.
Lesson
A persistence layer changes what an interface can promise: once conversations were stored rather than held in memory, a reload stopped being a data-loss event. Designing the client/server protocol first made both sides straightforward.
Features (5)
Token-by-token streaming over SSE · persistent conversations · Markdown rendering · syntax highlighting with copy-code · authentication surviving reload
Repository
github.com/jhraihan/llm_powered_ai_chatbot

4. MediDesk

Healthcare

Hospital management system with four-role access control.

React (4 role views) → Django + DRF (JWT + RBAC) → Database
Problem
Hospital workflows are a permissions problem before they are a software problem. A receptionist books appointments but must not read clinical notes; a doctor issues prescriptions but does not manage billing; a patient sees only their own records.
Approach
JWT authentication with module access restricted by role across four roles. Appointments, prescriptions, records, billing and a medicine catalogue each expose only permitted operations.
Hardest problem
Modelling a prescription properly. Storing it as text would have been quick, but a prescription is genuinely structured: one consultation links to several medicines, each with its own dosage and duration. Four roles also made access control harder than the three-role projects — each module had to be reasoned about separately rather than governed by one blanket rule.
Lesson
The schema decides what the application can do later. Because prescriptions were modelled as real relations, catalogue search and dosage linking came almost for free; a text field would have required a migration and a rewrite. An appointment is also a lifecycle, not a row — booked, approved, completed and cancelled are states with rules about legal transitions.
Features (7)
Four-role JWT authentication · appointment management with filtering · structured prescriptions · doctor & patient portals · real-time availability toggle · billing & invoicing · searchable medicine inventory
Repository
github.com/jhraihan/hospital-management-system-django-react

5. PromptCanvas

AI Application

Text-to-image generation with stored results.

React (prompt input) → Django (server-side call) → PostgreSQL  ·  branch: Hugging Face
Problem
Built to work through what it takes to put a generative model behind a real interface: handling a request that takes seconds rather than milliseconds, keeping the model call server-side, and storing what comes back.
Hardest problem
Latency breaks the usual assumptions — the interface must communicate that work is happening, and the backend holds a request open far longer than a typical API call. Keeping the model call server-side was the other constraint: the browser never contacts the inference API directly, so the credential stays on the server.
Lesson
What it takes to put an external model behind an interface rather than call it from a script. Storing generated images rather than discarding them turned a one-shot tool into something with history.
Features (3)
Text-to-image generation via Hugging Face · image storage and retrieval · authentication required
Repository
github.com/jhraihan/tech-store-platform-django-react

Naming trap — do not repeat

The hero size was originally named display-xl. Tailwind failed to generate it because it collides with the existing display key, silently falling back to 16px. It was renamed to hero. Avoid font-size keys that prefix-collide with existing ones. Note also that Tailwind config changes require a Vite restart — they are not hot-reloaded.

6.4 Motion

EffectBehaviour
Scroll revealFade and 16px rise as elements enter the viewport
TypewriterHero line cycles five phrases with a blinking caret

Non-negotiable motion rule

Content must never depend on an animation to become visible. The Reveal component enforces this two ways: reduced-motion renders a plain element with no animation, and a 900ms timer reveals the element regardless — so a missed intersection (a collapsed grid child, an offscreen container, a browser without IntersectionObserver) can never leave real content stuck at zero opacity.

This rule exists because it was violated once: case study sections rendered into the DOM but stayed permanently invisible, because whileInView never fired inside a collapsed grid. Every section of every case study was affected.

08Feature Specifications

8.1 Architecture diagrams

The highest-value feature. Each case study renders a request-flow diagram as inline SVG — no image request, crisp at any zoom, inheriting theme tokens. Flow definitions live in frontend/src/components/ArchitectureDiagram.jsx; a project with no defined flow renders nothing rather than an empty frame.

Each diagram is framed in terminal-window chrome with a caption, uses colour-coded nodes, and optionally hangs an external service off the API node as a dashed branch. IntelliChat's connectors animate to signify streaming. On narrow screens the flow stacks vertically with downward connectors, so no node is ever clipped.

Rationale: this shows systems thinking rather than claiming it, and gives an interviewer something concrete to ask about.

8.2 Command palette

Opened with Cmd/Ctrl + K from anywhere. Groups results into Navigation, Case studies, Actions and Links. Actions are derived from live data, so a newly added project appears without code changes. Full keyboard control: arrows navigate, Enter selects, Escape closes — Escape is bound at the document so it works regardless of focus.

8.4 Media placeholders

ImageFrame renders a designed placeholder when no image exists: a dotted field with corner ticks, holding the correct aspect ratio. It reads as part of the design rather than as an error, which is what allows the site to ship before screenshots exist. Supplying an image later requires no other change. The component also falls back to the placeholder if an image fails to load.

8.5 Project filtering

The active filter lives in the URL query string, so a filtered view is shareable and survives refresh and back-navigation. Only nine interview-relevant technologies are offered as filters — listing all 34 turns the control into a wall of buttons nobody reads.
