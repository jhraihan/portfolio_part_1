01How the system fits together

Two Render services and one Neon database. Both services build from the same GitHub repository, main branch.

Visitor → portfolio-web (static React build) → portfolio-api (Django + gunicorn) → Neon PostgreSQL
portfolio-api → WhiteNoise → backend/media/ (photo, CV, screenshots — committed to git)
PieceRender typeRoot dirWhat it does
portfolio-webStatic Sitefrontend The React single-page app. Never sleeps; loads instantly.
portfolio-apiWeb Service (Python 3.12)backend The REST API, the admin CMS, and the media files. Sleeps after 15 minutes idle.
NeonExternal— PostgreSQL. Holds every piece of text, every project, every contact message. Survives deploys.
Why Neon, not Render Postgres

Render's free database is deleted after 30 days. Neon's free tier does not expire.

Why media is committed to git

Render's disk is ephemeral: it is rebuilt from the repository on every deploy, and anything written to it at runtime is lost. In production Django does not serve media itself; WhiteNoise does, and WhiteNoise only knows about files that existed when the server started. So a file is served only if it is in backend/media/ in the repository. This is why backend/media/ is deliberately not in .gitignore.

02What happens when you push

A push to main triggers both services to rebuild automatically. Changing an environment variable in the Render dashboard also triggers a redeploy of that service.

2.1 Backend — backend/build.sh

Every step is safe to repeat. Steps 5 and 6 rewrite content from seed_portfolio.py, so they overwrite admin edits to projects and to profile wording (see 5.2).

#StepWhat it does
1pip install -r requirements/prod.txtInstalls Django, DRF, gunicorn, WhiteNoise.
2collectstaticGathers admin CSS/JS for WhiteNoise.
3migrateApplies any new database migrations to Neon.
4seed_portfolioOnly if the database has no projects. Loads all content on a brand-new database.
5sync_projectsWrites every project in seed_portfolio.py — text, features, technologies, GitHub, live and video links — creating new ones and updating existing ones. Deletes any project named in REMOVED_PROJECTS. Never touches covers or screenshots.
6sync_profile_copyPushes profile wording from seed_portfolio.py to the live database. Never touches photo, CV or links.
7attach_mediaFills a cover, gallery, photo or CV that is empty or points at a file that no longer exists, linking it to the committed files. Anything intact is left alone.
8create adminCreates the admin user from ADMIN_USERNAME / ADMIN_PASSWORD if that user does not exist yet.

Then Render starts the server:

gunicorn config.wsgi:application --bind 0.0.0.0:$PORT

Render's health check calls /api/profile/. If it fails, the old version keeps running.

2.2 Frontend

npm ci && npm run build      # publishes frontend/dist
  • VITE_API_URL is baked in at build time. Changing it requires a redeploy of portfolio-web, not just the backend.
  • A rewrite rule /* → /index.html makes URLs like /projects/micromart work on refresh. It must be Rewrite, not Redirect. Render ignores the _redirects file in public/.

2.3 Timeline of a normal deploy

  1. git push — both services start building.
  2. Frontend finishes in about 1–2 minutes.
  3. Backend takes about 3–5 minutes (dependency install dominates).
  4. Watch progress in Render → service → Events / Logs.
  5. Run the after-deploy checklist (section 08).

Why admin uploads fail

The admin's upload button saves the file to Render's disk and points the database at it. WhiteNoise never serves the file because it did not exist at startup, so the site shows a broken image. The next deploy deletes the file anyway. Use the admin for text only.

05Workflows — making common changes

Backend commands run from backend/ with the virtual environment active (venv\Scripts\activate on Windows). Frontend commands run from frontend/.

5.1 Change code (any feature, fix or design change)

# 1. Test locally
cd backend  && python manage.py test          # all backend tests must pass
cd frontend && npm test && npm run lint && npm run build

# 2. Look at what you are about to commit
git status
git diff

# 3. Commit and push
git add <files>
git commit -m "Describe the change"
git push

Then watch both services in Render and run the checklist in section 08.

5.2 Change text on the site

Projects and profile wording: edit seed_portfolio.py — the PROJECTS list, or the narrative fields of PROFILE (title, tagline, hero intro, about text, availability, meta description) — then commit and push. Every deploy writes them to the live database through sync_projects and sync_profile_copy, so an admin edit to any of these is put back on the next deploy.

Everything else — skills, education, coursework, and the profile's links and email — is edited in the admin and survives deploys:

  1. Open https://portfolio-api-9028.onrender.com/admin/ and sign in.
  2. Edit the entry. Save.
  3. Reload the website. No deploy needed.

5.3 Replace the profile photo or CV

# 1. Drop the new file into the git-ignored source folder
#    photo -> images/      CV (PDF) -> cv/

# 2. Optimise it into backend/media/ and update the local database
python manage.py update_profile_media --dry-run       # preview
python manage.py update_profile_media                 # or --photo-only / --cv-only

# 3. Commit the media and push
git add backend/media
git commit -m "Update profile photo"
git push

On deploy, build.sh notices the live database points at a file that no longer exists and re-links it to the newest file in media/profile/. No admin step is needed.

If you replace the photo but keep the same filename, the live record is still valid, so nothing needs re-linking; browsers may show the old picture until their cache expires.

5.4 Change project screenshots

Screenshot filenames are listed by hand in two commands. Both need updating:

  1. Put the new screenshots in images/<project-folder>/.
  2. In backend/apps/projects/management/commands/import_media.py, update COVERS and CAPTIONS for that project if the cover or captions change.
  3. Run python manage.py import_media. It optimises the images into backend/media/projects/ and updates your local database.
  4. In backend/apps/projects/management/commands/attach_media.py, update COVERS and GALLERIES to the new output filenames.
  5. Commit backend/media and both command files, then push.
  6. If the old files were deleted, the next deploy notices the gallery points at missing files and re-links it on its own. If they were kept, re-link it with attach_media --force against production (section 06).
Note

attach_media --force rebuilds every gallery, so captions return to the values in attach_media.py. Keep captions edited in the admin in step with that file.

5.5 Add or remove a project

  1. Add the project to PROJECTS in seed_portfolio.py. A project created only in the admin is not deleted by a deploy, but it is invisible to the seed and is lost if the database is ever rebuilt.
  2. Add its screenshots as in 5.4, adding the new slug to the mappings in both commands. import_media --project <slug> imports just that project.
  3. Add an architecture flow for the slug in frontend/src/components/ArchitectureDiagram.jsx, or the case study shows no diagram.
  4. Regenerate the sitemap, then commit and push: 
    python manage.py generate_sitemap --base-url https://portfolio-web-asu3.onrender.com

To remove a project, delete it from PROJECTS and add its slug to REMOVED_PROJECTS in the same file. Deleting it from the list alone leaves it live, because sync_projects only deletes what it is told to. Then remove its diagram flow, its entries in both media commands and its files under backend/media/, and regenerate the sitemap.

5.6 Change a dependency or the database schema

  • New Python package: add it to backend/requirements/base.txt (or prod.txt if production-only). Render installs it on the next build.
  • Model change: run python manage.py makemigrations locally, commit the migration file. build.sh applies it to Neon. Never edit a migration that is already deployed.
  • New npm package: npm install <pkg> and commit both package.json and package-lock.json. npm ci fails if they disagree.
  • New environment variable: add it to backend/.env.example with a comment, and to the Render dashboard before pushing code that needs it.

06Running a command against production

Render's free tier has no shell. To run a management command on the live database, run it on your own machine with DATABASE_URL pointed at Neon. Your local backend/media/ must match what is pushed, because file checks read your local disk.

Git Bash

cd backend
DATABASE_URL="<Neon connection string>" USE_SQLITE=False python manage.py <command>

PowerShell

cd backend
$env:DATABASE_URL="<Neon connection string>"; $env:USE_SQLITE="False"
python manage.py <command>
Remove-Item Env:DATABASE_URL, Env:USE_SQLITE      # back to local afterwards

Copy the connection string from Render → portfolio-api → Environment, or from the Neon dashboard.

CommandUse it to
changepassword <username>Reset the admin password.
attach_mediaRepair a broken photo or CV link immediately, without waiting for a deploy.
attach_media --forceRe-link every cover, gallery, photo and CV to the committed files.
sync_profile_copyPush profile wording from seed_portfolio.py.
sync_projectsPush project text and links from seed_portfolio.py without waiting for a deploy.
Be careful

This is the real database. Never run seed_portfolio, flush, import_media or update_profile_media this way. Unset the variables afterwards so later local commands do not touch production by accident.

07The admin account

  • URL: https://portfolio-api-9028.onrender.com/admin/
  • Credentials: the values of ADMIN_USERNAME and ADMIN_PASSWORD in Render → portfolio-api → Environment. They are not stored anywhere in the repository.
  • Once you can log in, delete ADMIN_PASSWORD from Render. The account stays; the build only creates it when it does not exist and never changes an existing password.
  • Forgotten password: changepassword against production (section 06).
  • Change the password from inside the admin (top right → Change password) whenever you like.

08Checklists

8.1 Before every push

  • ☐ python manage.py test passes
  • ☐ npm test, npm run lint and npm run build pass
  • ☐ git status shows only files you meant to change
  • ☐ No .env file tracked: git ls-files | grep -c "\.env$" prints 0
  • ☐ New images or CV are in backend/media/ and staged
  • ☐ New environment variables already added in Render
  • ☐ New migrations committed

8.2 After every deploy

The first request may take about 50 seconds if the backend was asleep.

  • ☐ Both services show Live in Render, with the latest commit
  • ☐ /api/profile/ returns JSON
  • ☐ Hero shows your name and photo
  • ☐ All project cards show screenshots
  • ☐ A case study opens with its diagram and gallery
  • ☐ Refreshing /projects/micromart does not 404
  • ☐ Résumé downloads
  • ☐ A test contact message appears in the admin
  • ☐ Light/dark toggle works

Quick checks from a terminal (Git Bash)

# Which photo does the live API point at?
curl -s https://portfolio-api-9028.onrender.com/api/profile/ | grep -o '"photo":"[^"]*"'

# Does that file load? (expect 200)
curl -s -o /dev/null -w "%{http_code}\n" <photo URL from above>

# Does client-side routing survive a refresh? (expect 200)
curl -s -o /dev/null -w "%{http_code}\n" https://portfolio-web-asu3.onrender.com/projects/micromart

11Rules — what never to do

  • Never upload images or the CV through the admin. Commit them (5.3, 5.4).
  • Never add backend/media/ to .gitignore. The site's images would vanish on the next deploy.
  • Never commit .env or paste SECRET_KEY, DATABASE_URL or passwords anywhere public.
  • Never commit images/ or cv/. They hold full-resolution originals and personal details; only the optimised copies belong in git.
  • Never set DEBUG=True in production. It exposes settings and stack traces to visitors.
  • Never run seed_portfolio against production.
  • Keep the API read-only except POST /api/contact/.
  • Push only after both test suites pass.

12Custom domain (optional)

  1. Buy a domain, then Render → portfolio-web → Settings → Custom Domain. Follow the DNS instructions.
  2. Add the new origin to CORS_ALLOWED_ORIGINS and CSRF_TRUSTED_ORIGINS on the backend.
  3. Update the canonical link and both og:url tags in frontend/index.html.
  4. Regenerate the sitemap with the new --base-url, commit, and push.
